Playwright cheat sheet
1. What is Playwright and how is it different from Selenium?
Playwright is an end-to-end testing framework developed by Microsoft. It supports Chromium, Firefox, and WebKit browsers with auto-waiting and faster execution. Unlike Selenium, it does not require external drivers and provides built-in tracing, video, and parallel execution support.
2. What are Browser, Context, and Page in Playwright?
  • Browser: Actual browser instance (Chrome/Firefox/WebKit)
  • Context: Isolated session like incognito window
  • Page: A single tab inside a context

Playwright - Browser, Browser Context & Page

In Playwright, Browser, Browser Context, and Page form a hierarchy. Understanding these three concepts is one of the most common Playwright interview questions.

Hierarchy

Browser ├── Context 1 │ ├── Page A │ └── Page B │ └── Context 2 ├── Page C └── Page D

1. Browser

A Browser is the actual browser instance such as Chromium, Firefox, or WebKit. 


const browser = await chromium.launch();

Think of it as:

  • Launching Google Chrome
  • Launching Microsoft Edge
  • Launching Firefox

Responsibilities

  • Starts the browser process.
  • Can contain multiple browser contexts.
  • Consumes the most system resources.
  • Needs to be closed after execution.

Example


const browser = await chromium.launch({
    headless: false
});

2. Browser Context

A Browser Context is an isolated browser session. 


            const context = await browser.newContext();

Think of it as:

  • Chrome Incognito Window
  • Separate Browser Profile

Each Context Has Its Own

  • Cookies
  • Local Storage
  • Session Storage
  • Authentication State
  • Cache

Example


            const user1 = await browser.newContext();

            const user2 = await browser.newContext();

Both users are completely independent.

3. Page

A Page represents a single browser tab. 


            const page = await context.newPage();

Think of it as:

  • A Chrome Tab
  • A Firefox Tab

Example


                const page = await context.newPage();

                await page.goto("https://example.com");

Interact With Elements


              await page.fill("#username", "john");

              await page.click("#login");

Complete Example


              const { chromium } = require("playwright");

(async () => {

    const browser = await chromium.launch();

    const context = await browser.newContext();

    const page = await context.newPage();

    await page.goto("https://example.com");

    console.log(await page.title());

    await browser.close();

})();

Execution Flow

  1. Launch Browser
  2. Create Browser Context
  3. Create Page
  4. Navigate to Website
  5. Perform Automation
  6. Close Browser

Why Browser Context Matters

Without Context


const page1 = await browser.newPage();

const page2 = await browser.newPage();

Both pages share:

  • Cookies
  • Login Session
  • Local Storage

With Context


const context1 = await browser.newContext();

const context2 = await browser.newContext();

const page1 = await context1.newPage();

const page2 = await context2.newPage();

Now both pages behave like completely different users.

Example

  • Context 1 → Admin User
  • Context 2 → Customer User

This is useful for multi-user testing like Chat Applications, Banking Systems, or E-commerce applications.

3. What is auto-waiting in Playwright?
Playwright automatically waits for elements to be Visible, Stable, and Enabled before performing any actions, reducing the need for manual waits.

Auto-waiting is one of Playwright's most powerful features. It automatically waits for elements to become ready before performing actions like click(), fill(), check(), or selectOption(). This eliminates the need to add unnecessary sleep() or manual waits, making tests faster and more reliable.

Before performing an action, Playwright checks that the element is:

  • ✅ is it Present in the DOM The element exists in the Document Object Model (DOM).
  • ✅ is it Visible The element is visible to the user (not hidden).
  • ✅ is it Stable The element is not moving, animating, or changing position.
  • ✅ is it Enabled The element is enabled and can be interacted with (not disabled).
then performs action

4. Difference between locator() and page.$()?
  • locator() is Playwright's modern and recommended way of finding elements. It supports auto-waiting, retryability, and always interacts with the latest state of the element.
  • page.$() returns an ElementHandle immediately and does not provide auto-waiting or retryability. It is generally discouraged in favor of locator().
  • locator() supports auto-waiting and is recommended
  • page.$() returns element handle without auto-waiting

12. What is Playwright Trace Viewer?
Trace Viewer is a debugging tool that helps analyze test failures. It shows screenshots, DOM snapshots, network requests, and actions step-by-step. It is very useful for identifying flaky tests and root causes of failures.
13. How do you run tests in parallel in Playwright?
Playwright runs tests in parallel by default using workers. You can also configure it in the config file. 
workers: 4
This improves execution speed significantly.
14. How do you handle flaky tests?
To handle flaky tests:
  • Use stable locators like data-testid
  • Avoid hard waits (setTimeout)
  • Use Playwright auto-waiting features
  • Use trace viewer for debugging
  • Avoid dependency between tests

16. What are fixtures in Playwright?
Fixtures are used to set up and tear down test environments. They help share common setup logic like browser, page, or login state across tests.

Test isolation means each test runs independently in a separate browser context. This prevents shared state like cookies or sessions from affecting other tests.

REST API (Representational State Transfer Application Programming Interface) is a set of rules that allows two applications to communicate over HTTP. It enables a client (such as a web application, mobile app, or automation script) to send requests to a server and receive responses.

Interview Definition (30-second Answer)

REST API stands for Representational State Transfer Application Programming Interface. It is an architectural style that allows a client and server to communicate over HTTP. REST APIs use standard HTTP methods such as GET, POST, PUT, PATCH, and DELETE to perform CRUD operations. They are stateless, meaning each request contains all the information needed to process it, and they commonly exchange data in JSON format.

How You Test REST APIs (QA Interview Answer)

As a QA Engineer, I typically verify the following aspects of a REST API:

  • API Endpoint (URL): Verify that the request is sent to the correct endpoint.
  • HTTP Method: Ensure the correct method is used (GET, POST, PUT, PATCH, DELETE).
  • Request Headers: Validate headers such as Content-Type, Authorization, Accept, and custom headers.
  • Request Payload (JSON): Verify the request body contains valid JSON with the required fields and correct data types.
  • JSON Schema Validation: Verify that the response follows the expected JSON schema, including required fields and data types.
  • Response Body: Validate that the response data is accurate, complete, and matches the expected values.
  • HTTP Status Code: Check that the API returns the correct status code (200, 201, 400, 401, 404, 500, etc.).
  • Response Time: Ensure the API responds within the acceptable performance threshold.
  • Authentication: Validate authentication mechanisms such as Bearer Token, OAuth, API Key, or Basic Authentication.
  • Error Handling: Test invalid inputs, missing mandatory fields, invalid authentication, and unauthorized access to ensure proper error responses are returned.
33. Hard assertion and soft Assertion

Hard Assertion

A Hard Assertion immediately stops the test execution if the assertion fails.

Behavior:

If the assertion passes → Test continues. If the assertion fails → Test stops immediately.

Soft Assertion

A Soft Assertion records the failure but does not stop the test immediately. The remaining test steps continue to execute.

35. What are the different waitFor methods we have

Playwright Wait Methods

Method Purpose Example
waitForLoadState() Wait for the page to reach a specific load state. await page.waitForLoadState('load');
waitForURL() Wait for the page URL to change. await page.waitForURL('**/dashboard');
waitForEvent() Wait for browser or page events. await page.waitForEvent('popup');
waitForResponse() Wait for a specific API response. await page.waitForResponse(res => res.url().includes('/login'));
waitForRequest() Wait for a specific API request. await page.waitForRequest(req => req.url().includes('/login'));
waitForFunction() Wait until a JavaScript condition becomes true. await page.waitForFunction(() => window.appReady);
locator.waitFor() Wait for a locator to reach a specific state. await page.locator('#loader').waitFor({ state: 'hidden' });
waitForTimeout() Pause execution for a fixed amount of time. await page.waitForTimeout(3000); (Not recommended for normal tests)

⚠️ Note: Prefer Playwright's built-in auto-waiting or explicit waits such as waitForResponse(), waitForURL(), or locator.waitFor() instead of waitForTimeout().

36.What is Playwright Architecture

Playwright follows a Client → Playwright Server → Browser architecture.

First, I write my automation script using the Playwright API in languages like TypeScript or JavaScript which are all we can call them as Client. When I execute the test, the API calls are sent to the,Playwright Server, which is a Node.js process. then the The Playwright Driverconverts these commands into browser-specific instructions and communicates directly with the browser to perform actions such as clicking, typing, navigating, and validating elements.

Inside the browser, Playwright uses three main objects:

  • Browser – Represents the browser instance.
  • Browser Context – Represents an isolated browser session with its own cookies, cache, local storage, and session storage. This allows us to simulate multiple users in the same browser.
  • Page – Represents a browser tab where all interactions such as clicking, typing, and assertions are performed.

One of Playwright's key features is Auto-Waiting. Before performing actions like click() or fill(), Playwright automatically waits for the element to:

  • Exist in the DOM
  • Be Visible
  • Be Enabled
  • Be Stable (not moving)
  • Be Ready for Interaction

This reduces flaky tests and eliminates the need for many explicit waits.

Overall, because Playwright communicates directly with browser engines, supports isolated browser contexts, and provides built-in auto-waiting, it delivers faster, more reliable, and efficient browser automation compared to traditional WebDriver-based tools.

30-Second Interview Answer

Playwright uses a Client → Driver → Browser architecture. The test script sends commands to the Playwright Driver, which communicates directly with Chromium, Firefox, or WebKit using native browser protocols. Inside the browser, we create Browser Contexts for isolated user sessions and Pages for browser tabs. Playwright also provides built-in Auto-Waiting, making tests faster, more stable, and more reliable without requiring browser drivers like ChromeDriver.
